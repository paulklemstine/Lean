## Theorem Target 1: Local Euler factor uniqueness from Frobenius trace data

### Precise theorem statement

If two good local Euler data packages for an elliptic curve over a finite field have the same residue characteristic and the same Frobenius trace, then their local Euler polynomials agree coefficientwise.

This is the theorem that upgrades “trace extraction works” into “the local factor is canonically determined.” It is the formal hinge between point-count computations and Euler product constructions.

### Lean 4 target signature

Use the existing `LocalEulerData` API and adapt names to the catalog if needed:

```lean
theorem local_euler_factor_ext_of_trace
  {K : Type*} [Field K]
  (d₁ d₂ : LocalEulerData K)
  (hp : d₁.goodPrime = d₂.goodPrime)
  (ha : d₁.frobeniusTrace = d₂.frobeniusTrace) :
  d₁.eulerFactor = d₂.eulerFactor
```

If `eulerFactor` is represented as a polynomial:

```lean
theorem local_euler_poly_ext_of_trace
  {K : Type*} [Field K]
  (d₁ d₂ : LocalEulerData K)
  (hp : d₁.goodPrime = d₂.goodPrime)
  (ha : d₁.frobeniusTrace = d₂.frobeniusTrace) :
  d₁.eulerPoly = d₂.eulerPoly
```

And if the library already contains something like `frobenius_trace_unique_value`, strengthen it to an extensionality theorem for the entire local factor.

### Why this is a breakthrough

This theorem turns local point-counting into a certified generator of Euler factors. Once formalized, it means any verified computation of `a_p` immediately determines the correct local factor, which is exactly what is needed for:
- formal Sato–Tate experiments,
- certified `L`-series coefficient extraction,
- and future machine-checked comparisons of local and global arithmetic invariants.

This is the “local identifiability theorem” for the BSD stack.

### Proof strategy options

#### Strategy A: coefficient comparison from the standard degree-2 formula
1. Unfold the definition of the good-prime Euler polynomial, typically `1 - a_p T + p T^2`.
2. Rewrite both sides using `hp` and `ha`.
3. Conclude by polynomial extensionality / coefficient comparison.

**Why promising:** This is likely the shortest and most robust Lean proof if the API already exposes the good-reduction formula.

#### Strategy B: uniqueness via point-count identity
1. Use the certified relation `#E(F_p) = p + 1 - a_p`.
2. Deduce equality of point counts from equality of traces.
3. Reconstruct the Euler factor from point-count data and conclude equality.

**Why promising:** Better if the current catalog has stronger theorems about point counts than about explicit polynomial formulas.

#### Strategy C: extensionality through `X`-adic evaluation
1. Show the local factor is determined by its coefficients at degrees `0,1,2`.
2. Prove equality of constant, linear, and quadratic coefficients separately.
3. Package into a generic extensionality lemma reusable for other local factors.

**Why promising:** This yields a reusable abstraction for higher-dimensional motives later.

**Most promising:** Strategy A, unless the current local data API hides the polynomial formula behind an abstract constructor.

### Cross-domain connection

This is an arithmetic-geometric analogue of **identifiability in inverse problems**: local arithmetic data determine the latent dynamical object (Euler factor). It also mirrors **system identification** in control theory, where a transfer function is reconstructed from observed response coefficients.

### Application keywords

## Theorem Target 2: Algebraic BSD side is strictly positive under standard hypotheses

### Precise theorem statement

Assume a `BSDData` package whose constituent invariants are all positive/nonzero in the expected sense: real period positive, regulator nonnegative (or positive in positive rank), Tamagawa factors positive, torsion order nonzero, and `|Sha|` positive. Then the algebraic side of BSD is strictly positive.

This theorem is foundational because ratio statements such as
`L*(E,1) / bsdAlgebraicSide(E)`
are mathematically meaningless unless the denominator is certified nonzero and preferably positive.

### Lean 4 target signature

A schematic target:

```lean
theorem bsdAlgebraicSide_pos
  (D : BSDData)
  (hΩ : 0 < D.realPeriod)
  (hR : 0 < D.regulator)
  (hSha : 0 < D.shaCard)
  (hTamagawa : 0 < D.tamagawaProduct)
  (hTor : 0 < D.torsionOrder) :
  0 < D.bsdAlgebraicSide
```

If the formula uses `torsionOrder^2` in the denominator, you may need:

```lean
theorem bsdAlgebraicSide_ne_zero
  (D : BSDData)
  (hΩ : D.realPeriod ≠ 0)
  (hR : D.regulator ≠ 0)
  (hSha : D.shaCard ≠ 0)
  (hTamagawa : D.tamagawaProduct ≠ 0)
  (hTor : D.torsionOrder ≠ 0) :
  D.bsdAlgebraicSide ≠ 0
```

And ideally both.

### Why this is a breakthrough

This theorem upgrades the BSD algebraic side from a symbolic expression to a certified positive quantity. That matters because:
- it enables safe division in verified numerical checks,
- it isolates exactly which hypotheses are needed for formal rank-0/rank-1 BSD comparisons,
- and it provides the positivity skeleton needed for future interval-arithmetic verification of the BSD ratio.

This is the theorem that lets the formal system distinguish a genuine arithmetic quantity from a merely syntactic fraction.

### Proof strategy options

#### Strategy A: unfold the formula and use ordered-field positivity lemmas
1. Expand `bsdAlgebraicSide` into product/quotient form.
2. apply `mul_pos`, `div_pos`, `pow_pos`, and positivity of finite products.
3. close denominator nonvanishing side-goals via positivity.

**Why promising:** Direct and likely fully supported by Mathlib’s ordered algebra hierarchy.

#### Strategy B: prove generic positivity lemmas for weighted products first
1. Introduce a reusable theorem: a finite product of positive terms is positive.
2. Separate numerator positivity and denominator positivity.
3. Instantiate for BSD invariants.

**Why promising:** Better architectural payoff if the existing scaffold uses lists/finsets of local factors.

#### Strategy C: factor through a normalized “log-BSD side”
1. Define a logarithmic version of the algebraic side for positive data.
2. Prove finiteness and real-valuedness there.
3. exponentiate back to positivity.

**Why promising:** More sophisticated, but opens the door to asymptotic/statistical study of BSD quantities.

**Most promising:** Strategy A for immediate theorem delivery; Strategy B if you want reusable infrastructure for later global products.

### Cross-domain connection

This is the arithmetic analogue of a **partition function positivity theorem** in statistical mechanics: before studying asymptotics or fluctuations, one must prove the state-sum is a genuine positive observable. It also resembles **well-posedness certificates** in numerical analysis.

### Application keywords

## Theorem Target 3: Regulator nondegeneracy from positive-definite height pairing

### Precise theorem statement

Let `V` be the Mordell–Weil free part tensored with `ℝ`, equipped with a symmetric bilinear Néron–Tate height pairing. If the pairing is positive definite on a chosen basis, then the regulator (the determinant of the Gram matrix) is strictly positive.

This is the exact theorem needed to justify the regulator term in BSD as a nonzero geometric invariant, not merely a formal determinant.

### Lean 4 target signature

A schematic linear-algebraic theorem, independent of elliptic curves at first:

```lean
theorem regulator_pos_of_posDef
  {n : Type*} [Fintype n] [DecidableEq n]
  (M : Matrix n n ℝ)
  (hsym : M.IsSymm)
  (hpd : M.PosDef) :
  0 < M.det
```

Then an arithmetic corollary:

```lean
theorem bsd_regulator_pos_of_height_pairing_posDef
  (D : BSDData)
  (hpd : D.heightPairingMatrix.PosDef) :
  0 < D.regulator
```

If `Matrix.PosDef` is not the exact Mathlib name, target the available positive-definite API (`LinearMap.IsPositive`, quadratic form positivity, or Sylvester-style criteria).

### Why this is a breakthrough

A formal BSD program without a regulator-positivity theorem is missing one of its geometric pillars. Proving this theorem:
- locks the regulator into the ordered-analytic world needed for ratio comparisons,
- connects arithmetic geometry to mature linear algebra in Mathlib,
- and creates a reusable determinant-positivity toolkit for heights, pairings, and Arakelov-style constructions.

This is the first step toward a formal theory of canonical heights robust enough for real BSD proofs.

### Proof strategy options

#### Strategy A: use existing Mathlib positive-definite matrix determinant theorem
1. Translate the height pairing matrix into the Mathlib notion of positive definiteness.
2. Apply the library theorem that positive-definite real symmetric matrices have positive determinant.
3. identify the regulator with that determinant.

**Why promising:** Fastest if the linear algebra theorem already exists.

#### Strategy B: Cholesky or Gram decomposition
1. Show a positive-definite symmetric matrix admits a factorization `M = Aᵀ A`.
2. Deduce `det M = (det A)^2`.
3. use invertibility / positive definiteness to conclude strict positivity.

**Why promising:** Conceptually clean and likely reusable in future Arakelov formalizations.

#### Strategy C: induction via principal minors (Sylvester criterion)
1. Prove positivity of all leading principal minors.
2. Deduce positivity of the full determinant.
3. package as a criterion theorem for arithmetic Gram matrices.

**Why promising:** Strongest infrastructure payoff, especially for explicit rank computations.

**Most promising:** Strategy A if available; otherwise Strategy B is the best blend of conceptual clarity and formal tractability.

### Cross-domain connection

This connects BSD to **information geometry** and **Riemannian metrics**: the regulator is the volume form induced by the canonical height metric on the Mordell–Weil lattice. Positive definiteness implies positive volume, just as covariance matrices define positive entropy geometry in statistics.

### Application keywords

`regulator`, `Néron-Tate height`, `positive definite matrix`, `Gram determinant`, `Mordell-Weil lattice`, `formal linear algebra`, `Arakelov geometry`

## Theorem Target 4: Finite-product coherence for local-to-global BSD factors

### Precise theorem statement

If a global arithmetic quantity is defined as the product over a finite set of local factors, then reindexing by a bijection or replacing equal local factor functions leaves the product unchanged. Instantiate this to Tamagawa products or truncated Euler products in the BSD scaffold.

This sounds elementary, but in practice it is the theorem that makes global arithmetic definitions stable under different enumerations of bad primes, database orderings, or equivalent local presentations.

### Lean 4 target signature

A generic finite-product theorem:

```lean
theorem finset_prod_congr_bsd
  {α β : Type*} [DecidableEq α] [DecidableEq β]
  (s : Finset α) (t : Finset β) (e : α ≃ β)
  (h : ∀ a ∈ s, f a = g (e a))
  (hst : t = s.map e.toEmbedding) :
  ∏ a in s, f a = ∏ b in t, g b
```

And an arithmetic corollary such as:

```lean
theorem tamagawaProduct_invariant_under_reindex
  (D₁ D₂ : BSDData)
  (hbad : D₁.badPrimes = D₂.badPrimes)
  (hfac : ∀ p ∈ D₁.badPrimes, D₁.tamagawaFactor p = D₂.tamagawaFactor p) :
  D₁.tamagawaProduct = D₂.tamagawaProduct
```

### Why this is a breakthrough

This is the theorem that prevents the formal BSD program from becoming brittle. Arithmetic geometry is full of canonically defined products presented in noncanonical ways. A machine-checked global theorem needs reindexing invariance built into its foundations.

It also creates the exact infrastructure needed for:
- comparing LMFDB-imported data with internally generated data,
- proving database-order independence,
- and later defining truncated Euler products in analytic verification workflows.

### Proof strategy options

#### Strategy A: reuse `Finset.prod_bij` / `Finset.prod_congr`
1. Reduce to standard Mathlib reindexing lemmas.
2. specialize to local factor functions.
3. package the result into BSD-specific corollaries.

#### Strategy B: define a canonical multiset of local factors
1. Push all local factors into a multiset.
2. prove product depends only on the multiset.
3. derive invariance under any presentation.

#### Strategy C: categorical viewpoint on finite products
1. interpret the product as a fold over a commutative monoid.
2. use fold invariance under permutations/equivalences.
3. instantiate to arithmetic local factors.

**Most promising:** Strategy A for immediate theorem extraction; Strategy B if you want a stronger canonical-data architecture.

### Cross-domain connection

This is a formal version of **gauge invariance**: the global observable does not depend on local coordinate choices. It also mirrors **database schema invariance** in computer science, where equivalent encodings must yield identical aggregate outputs.

### Application keywords

`finite products`, `Tamagawa product`, `Euler product`, `reindexing invariance`, `commutative monoids`, `formal databases`, `canonical arithmetic data`
