# Future Directions — EML Single-Operator Church–Turing Thesis

This cycle established, with fully verified Lean 4 proofs (0 sorries, standard
axioms only), the **affirmative content** of the single-operator thesis:

* `EML/SingleOperatorRepresentability.lean` — grammars + semantics for the
  two-operator language `EMLExpr` (`exp`, `log`) and the single-operator language
  `EMLOnlyExpr` (sole primitive `eml(x,y) = exp(x) − log(y)`).
* `EML/SingleOperatorCompilation.lean` — bidirectional, semantics-preserving
  compilation and the equivalence `EMLOnlyRepresentable f ↔ EMLRepresentable f`,
  with linear size bounds (forward `≤ 5·size`).
* `EML/SingleOperatorChurchTuring.lean` — function-algebra closure of the class
  (`+, ×, neg, −, inv, exp, log, eml`), reverse size bound (`≤ 4·size`), concrete
  `sinh`/`cosh`/`pow`, and the omnibus `single_operator_church_turing`.
* `EML/SingleOperatorActivations.lean` — finite sum/product closure, polynomial
  completeness (`EMLOnlyRepresentable_mvPolynomial`), and representability of the
  standard activations (sigmoid, softplus, tanh, SiLU).

The following conjectures are concrete, falsifiable targets for the next cycles.

---

## C1. Necessity / minimality of the single operator

The field-operations-only fragment (no `eml`) represents **exactly** the
rational functions, and `exp` is not among them — so the transcendental primitive
is genuinely necessary, not eliminable.

> **Conjecture.** Define `FieldOnlyRepresentable` as the closure of constants and
> projections under `+, ×, neg, inv`. Then
> `FieldOnlyRepresentable f ↔ ∃ p q : MvPolynomial (Fin n) ℝ, f = (eval · p)/(eval · q)`
> (as total functions with junk-value `inv 0 = 0`), and
> `¬ FieldOnlyRepresentable (fun x : Fin 1 → ℝ => Real.exp (x 0))`.

*Attack.* The negative half follows from `exp` growing faster than any rational
function (`Real.tendsto_exp_div_pow_atTop` / transcendence of `exp` over `ℝ(x)`).

## C2. Tightness of the size bounds

The compilation overhead constants `5` (forward) and `4` (reverse) are optimal.

> **Conjecture.** There is a family `eₖ : EMLExpr` of `log`-only expressions with
> `(compileToEMLOnly eₖ).size = 5·eₖ.size − o(size)`, and dually a family of
> `eml`-only expressions saturating `compileFromEMLOnly_size_bound`. Equivalently,
> no compiler achieves constant `< 5` (resp. `< 4`) for all inputs.

## C3. Domain-faithful (partial) single-operator thesis

Our semantics is *total* (junk values `log x = 0` for `x ≤ 0`, `inv 0 = 0`). The
sharper statement uses the **partial** `Option ℝ` semantics (cf. the source
grammar `UExpr`/`EMLExpr` with `eeval` in the archived `EML/Defs.lean`).

> **Conjecture.** There is a compilation `UExpr → EMLExpr` (single primitive,
> partial semantics) that is *domain-faithful*: `t.eeval x = e.eval x` for all
> `x` **including the `none` (undefined) cases**, with the `eml` node guarded by
> its positivity side-condition. The size blow-up remains linear.

## C4. Stone–Weierstrass universality of the single-operator class

Combine `EML/StoneWeierstrassApprox.lean` with single-operator representability:
the single primitive is not just exactly-elementary but **approximation-universal**.

> **Conjecture.** For every compact `K ⊆ ℝⁿ` the single-operator representable
> functions are dense in `C(K, ℝ)` (uniform norm). Concretely, the subalgebra
> generated by `{x ↦ eml(⟨a,x⟩, 1) = exp(⟨a,x⟩) : a ∈ ℝⁿ}` separates points and
> contains constants, hence is dense by `eml_topologicalClosure_eq_top_of_separatesPoints`.

## C5. Differential-field closure of the single-operator class

The smooth single-operator functions form a differential field: closed under
`d/dx`, with the derivative again single-operator representable.

> **Conjecture.** If `f : ℝ → ℝ` is single-operator representable by an expression
> whose evaluation is differentiable on an open `U`, then `deriv f` is
> single-operator representable on `U`. The derivative of an `eml` node is
> `exp(a)·a' − b'/b` (see `hasDerivAt_eml_composition`), which is itself an `eml`-
> algebra term, so closure should follow by structural induction on the syntax.
