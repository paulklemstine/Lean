## Assignment: Direction 1: Multi-Invariant Theory Morphisms and Product Orders

Mode: **prove**

You should build a genuinely new abstraction layer, not a cosmetic generalization. The target is a certified calculus of **simultaneous invariant transfer**: one morphism should transport several logically independent certificates at once, with the same compositional clarity as the scalar `ℕ`-valued framework. This is the missing infrastructure for a large class of “bridge theorems” across arithmetic, tropical, analytic, and learning-theoretic domains.

The breakthrough is this: once invariants are allowed to live in product orders or more general semilattices, a single formal morphism can carry, for example, **height + entropy + rank + robustness** simultaneously. That changes the ontology of the library from “one theorem, one certificate” to “one theorem, a vector of interoperable guarantees.”

## Precise Theorem Targets

Work first with the concrete and highly Lean-friendly case of tuple-valued invariants `Fin k → ℕ`, ordered pointwise. Only after that, if the infrastructure is clean, expose the semilattice-valued generalization.

### Core definitions to introduce

A minimal first-pass design:

```lean
structure RichTheory (k : ℕ) where
  Carrier : Type
  Inv : Carrier → Fin k → ℕ

structure RichHom {k : ℕ} (T₁ T₂ : RichTheory k) where
  toFun : T₁.Carrier → T₂.Carrier
  mono_inv : ∀ x i, T₂.Inv (toFun x) i ≤ T₁.Inv x i
```

The variance above is chosen so a morphism **transfers upper bounds forward**: any certificate on `T₁.Inv x i` yields one on the image. If your local catalog suggests the opposite scalar convention, reverse all inequalities uniformly, but keep the theorem statements exact and compositional.

Define composition and identity:

```lean
def RichHom.id (T : RichTheory k) : RichHom T T := ...
def RichHom.comp {T₁ T₂ T₃ : RichTheory k} :
  RichHom T₂ T₃ → RichHom T₁ T₂ → RichHom T₁ T₃ := ...
```

## Exact Theorem Statements

### 1. Composition theorem for product-valued invariant transfer

This is the foundational theorem: product-order enrichment should not break the scalar transfer calculus.

```lean
theorem RichHom.comp_mono_inv
    {k : ℕ} {T₁ T₂ T₃ : RichTheory k}
    (g : RichHom T₂ T₃) (f : RichHom T₁ T₂) :
    ∀ x i, T₃.Inv ((g.toFun) ((f.toFun) x)) i ≤ T₁.Inv x i
```

You should also package this into the proof that `RichHom.comp g f` is again a `RichHom`.

A more structural theorem, if you define the order on invariant vectors explicitly:

```lean
def invVec {k : ℕ} (T : RichTheory k) (x : T.Carrier) : Fin k → ℕ := T.Inv x

theorem RichHom.monotone_vector
    {k : ℕ} {T₁ T₂ : RichTheory k} (f : RichHom T₁ T₂) :
    ∀ x, (∀ i, T₂.Inv (f.toFun x) i ≤ T₁.Inv x i)
```

This is simple, but it is the portal through which every future application will pass.

```lean
theorem ScalarHom.toRich_faithful
```

```lean
theorem scalar_hom_iff_rich_hom

    (∃ h : RichHom T₁.toRich T₂.toRich, h.toFun = f)
```

This theorem matters conceptually: it certifies that the enriched framework is not a parallel universe but a true extension of the existing one.

### 3. Dominance theorem: simultaneous coordinatewise control under composite transfer

This is the first nontrivial theorem with “research taste.” The point is not merely that composition exists, but that it **dominates every intermediate certificate in every coordinate simultaneously**.

For `f : T₁ → T₂` and `g : T₂ → T₃`, prove:

```lean
theorem composite_dominates_source
    {k : ℕ} {T₁ T₂ T₃ : RichTheory k}
    (f : RichHom T₁ T₂) (g : RichHom T₂ T₃) :
    ∀ x i, T₃.Inv (g.toFun (f.toFun x)) i ≤ T₁.Inv x i
```

and also the intermediate dominance:

```lean
theorem composite_dominates_intermediate
    {k : ℕ} {T₁ T₂ T₃ : RichTheory k}
    (f : RichHom T₁ T₂) (g : RichHom T₂ T₃) :
    ∀ x i, T₃.Inv (g.toFun (f.toFun x)) i ≤ T₂.Inv (f.toFun x) i
```

Then package these into a coordinatewise minimum statement if useful:

```lean
theorem composite_dominates_min
    {k : ℕ} {T₁ T₂ T₃ : RichTheory k}
    (f : RichHom T₁ T₂) (g : RichHom T₂ T₃) :
    ∀ x i, T₃.Inv (g.toFun (f.toFun x)) i ≤ min (T₂.Inv (f.toFun x) i) (T₁.Inv x i)
```

This theorem is the formal version of “a composite bridge preserves all tracked certificates at once.”

### 4. Product theorem for bundling independent scalar certificates into one rich certificate

This is where the abstraction becomes transformative. Given two scalar theories on the same carrier, package them into a 2-invariant theory and show that separate certificate-transfer lemmas assemble into a single rich morphism.

A clean version:

```lean
def pairTheory (α : Type) (I₁ I₂ : α → ℕ) : RichTheory 2 := ...

theorem mk_pair_rich_hom
    {α β : Type} {I₁ I₂ : α → ℕ} {J₁ J₂ : β → ℕ}
    (f : α → β)
    (h₁ : ∀ x, J₁ (f x) ≤ I₁ x)
    (h₂ : ∀ x, J₂ (f x) ≤ I₂ x) :
    RichHom (pairTheory α I₁ I₂) (pairTheory β J₁ J₂)
```

Then prove explicit coordinate projections:

```lean
theorem mk_pair_rich_hom_coord0 ...
theorem mk_pair_rich_hom_coord1 ...
```

This theorem is the formal gateway to applications built from existing catalog theorems.

## Most Promising Generalization

After the `Fin k → ℕ` theory is stable, consider the lattice-valued version:

```lean
structure LatticeTheory (L : Type) [Preorder L] where
  Carrier : Type
  Inv : Carrier → L

structure LatticeHom (L : Type) [Preorder L]
    (T₁ T₂ : LatticeTheory L) where
  toFun : T₁.Carrier → T₂.Carrier
  mono_inv : ∀ x, T₂.Inv (toFun x) ≤ T₁.Inv x
```

If you push this to `[SemilatticeInf L]` or `[OrderBot L]`, you can later encode “joint certificates” not only as tuples, but as objects in abstract information orders, complexity lattices, or proof-resource hierarchies. But do not overbuild before the tuple case is complete and usable.

## Proof Strategy Architecture

### Strategy A: Direct pointwise order calculus on `Fin k → ℕ`
This is the safest and probably best first route.

1. Define `RichTheory` and `RichHom` with pointwise inequalities.
2. Prove identity and composition by direct transitivity:
   `T₃.Inv (g (f x)) i ≤ T₂.Inv (f x) i ≤ T₁.Inv x i`.
3. Build `pairTheory` and verify coordinatewise transfer by case split on `Fin 2`.

Why this is promising: Lean handles pointwise inequalities on functions very well, and this route minimizes typeclass friction. It yields a usable API fast.

---

### Strategy B: Abstract through the product order on function spaces
This is conceptually stronger and may scale better.

1. Define the invariant vector `invVec : Carrier → (Fin k → ℕ)`.
2. Use the instance `Pi.preorder` so that monotonicity is stated as
   `invVec (f x) ≤ invVec x`.
3. Prove composition once at the vector level, then derive coordinate lemmas by evaluation.

Why this is promising: it gives a clean theorem language and prepares the later jump to arbitrary lattice-valued invariants. It also makes the “dominance theorem” almost tautological.

---

### Strategy C: Start from a semilattice-valued abstraction, then specialize
This is the most visionary route, but only choose it if the scalar and tuple APIs are already conceptually aligned.

1. Formalize `LatticeTheory` over an arbitrary preorder.
2. Instantiate with `L = Fin k → ℕ`.
3. Recover all tuple theorems as corollaries.

Why this is risky: typeclass search and the design burden may slow down theorem production. Use only if you can keep the tuple case lightweight and avoid abstracting away computationally useful coordinate lemmas.

**Recommendation:** Start with Strategy A, refactor into Strategy B once the basic theorems are proved, and only then decide whether Strategy C is worth the additional abstraction.

## Cross-Domain Connection

This direction is more than order theory. It is a universal language for **multi-certificate transport** across disciplines.

- **Arithmetic geometry:** transfer height, valuation complexity, and entropic proxies simultaneously.
- **Tropical geometry:** track degree, rank, and robustness in one morphism.
- **Machine learning theory:** one certified map can carry Lipschitz constant, margin, and compression/rank bounds together.
- **Proof theory / formal verification:** one transformation can preserve cost, soundness margin, and resource bound at once.
- **Information theory:** a morphism can transport both signal magnitude and information loss constraints, foreshadowing a lattice semantics for data-processing-type inequalities.

The science-fiction leap is this: rich invariant morphisms could become the formal substrate for a **certificate compiler**, where proofs automatically aggregate heterogeneous guarantees into one compositional object.
