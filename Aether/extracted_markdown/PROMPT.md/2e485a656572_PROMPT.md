## Core Mathematical Objective

Formalize a general quantitative forking framework and instantiate it for Schnorr–Fiat–Shamir.

### Precise target theorem family

Let `G` be a finite cyclic group of prime order `q`, written multiplicatively or additively depending on the cleanest Mathlib interface available. Let `g : G` be a generator. Let `x : ZMod q` be a witness and `y = g^x` the public key. Let a Fiat–Shamir signature transcript be `(a, c, z)` satisfying the Schnorr verification equation
\[
g^z = a \cdot y^c.
\]
If an adversary in the random oracle model outputs a valid transcript with probability at least `ε`, and with non-negligible probability the challenge `c` is the answer to a distinguished oracle query on the commitment/public-input pair, then rewinding at that query yields two accepting transcripts
\[
(a,c,z),\quad (a,c',z')
\]
with `c ≠ c'`, from which one extracts
\[
x = (z-z') (c-c')^{-1} \pmod q.
\]

The quantitative theorem should not stop at existential extraction: it must provide an explicit lower bound of the form
\[
\Pr[\text{fork succeeds}] \ge \frac{\varepsilon^2}{q} - \frac{1}{q^2}
\]
or a provable variant that is mathematically correct under your formal assumptions, and then deduce an explicit extractor success bound and concrete reduction loss.

If the exact constants in the user-supplied conjecture are not derivable from the cleanest formal assumptions, **do not fake them**. Instead:
- prove the strongest correct theorem under precise hypotheses,
- isolate the gap as a named conjecture or stronger lemma,
- and test it computationally.

## Lean 4 Formalization Targets

### Suggested new definitions

```lean
structure SchnorrInstance (G : Type*) [Group G] (q : ℕ) where
  gen : G
  pub : G

structure SchnorrTranscript (G : Type*) (q : ℕ) where
  a : G
  c : ZMod q
  z : ZMod q

structure ForkedTranscript (G : Type*) (q : ℕ) where
  a : G
  c₁ c₂ : ZMod q
  z₁ z₂ : ZMod q
  hneq : c₁ ≠ c₂

def schnorrVerifies
  {G : Type*} [Group G] {q : ℕ}
  (gen pub : G) (tr : SchnorrTranscript G q) : Prop :=
  gen ^ (tr.z.val) = tr.a * pub ^ (tr.c.val)

def schnorrExtract
  {q : ℕ} [Fact q.Prime]
  (ft : ForkedTranscript G q) : ZMod q :=
  (ft.z₁ - ft.z₂) * (ft.c₁ - ft.c₂)⁻¹
```

If exponentiation via `Nat` is too awkward for the algebraic identity, it may be cleaner to work with an additive cyclic group and scalar multiplication by `ZMod q`, or to represent Schnorr over the additive group `ZMod q` first as a model theorem, then transport to abstract cyclic groups.

### Precise theorem statement with Lean-style signatures

You should aim for at least the following theorem cluster.

#### Theorem 1: Algebraic extraction from two accepting transcripts
```lean
theorem schnorr_extract_correct
  {q : ℕ} [Fact q.Prime]
  {G : Type*} [CommGroup G]
  (gen pub : G)
  (x : ZMod q)
  (hpub : pub = gen ^ (x.val))
  (ft : ForkedTranscript G q)
  (hacc₁ : schnorrVerifies gen pub
    { a := ft.a, c := ft.c₁, z := ft.z₁ })
  (hacc₂ : schnorrVerifies gen pub
    { a := ft.a, c := ft.c₂, z := ft.z₂ }) :
  gen ^ ((schnorrExtract ft).val) = pub
```

Stronger and preferable, if you can set up the scalar action cleanly:
```lean
theorem schnorr_extract_unique
  {q : ℕ} [Fact q.Prime]
  {G : Type*} [AddCommGroup G] [Module (ZMod q) G]
  [NoZeroSMulDivisors (ZMod q) G]
  (gen pub : G)
  (x : ZMod q)
  (hpub : pub = x • gen)
  (ft : ForkedTranscript G q)
  (hacc₁ : ft.z₁ • gen = ft.a + ft.c₁ • pub)
  (hacc₂ : ft.z₂ • gen = ft.a + ft.c₂ • pub) :
  schnorrExtract ft • gen = x • gen
```

This is the algebraic core: subtraction of verification equations, factorization, inversion in the field `ZMod q`.

#### Theorem 3: Concrete extractor success theorem for Schnorr–Fiat–Shamir
```lean
theorem schnorr_fs_extractor_success
  {q : ℕ} [Fact q.Prime]
  (A : SchnorrFSAdversary q)
  (ε : ℚ)
```

## Proof Strategy Architecture

You must provide at least 2–3 genuine proof avenues in the code comments / paper, and execute the strongest one.

### Strategy A: Algebra-first, probability-second
1. **Prove extraction algebraically** from two accepting transcripts with the same commitment and distinct challenges.
   - Use `field_simp`, cancellation in `ZMod q`, and group/module rearrangement.
   - This should be a deep multi-step `calc` proof, not a one-line simp.
2. **Define a finite rewinding experiment** as explicit sampling over challenge values and adversary randomness.
   - Represent random oracle answers as finite maps or challenge vectors.
   - Define “fork success” by equality of all pre-query randomness and divergence at the distinguished query.
3. **Count favorable pairs combinatorially** to derive the lower bound.
   - This is promising because Lean handles finite counting better than abstract measure-theoretic rewinding.
   - Most likely the best path if Mathlib probability interfaces become heavy.

**Why this is likely best:** it isolates the hard cryptographic insight into finite combinatorics and algebra over `ZMod q`, where Lean is strongest.

### Strategy B: Abstract probability with conditional events
1. Model adversary success as a random variable over coins and oracle responses.
2. Define the rewound execution by coupling two oracle samples sharing a prefix and differing at one challenge point.
3. Prove the lower bound using conditional probability, Jensen/Cauchy–Schwarz-style inequalities, or second-moment counting.

**Why this is deeper:** it yields a reusable framework for many Fiat–Shamir reductions, not just Schnorr.  
**Why it is harder:** Lean probability APIs can make even simple cryptographic arguments technically expensive.

### Strategy C: Start with a one-query special case, then generalize
1. Formalize a simplified adversary that makes exactly one oracle query and then outputs a transcript.
2. Prove the exact forking probability formula in this regime.
3. Extend to a distinguished-query adversary with transcript logging and query-index selection.

**Why this matters:** if the full Bellare–Neven statement is too broad for one cycle, this still yields a publishable, testable, machine-verified theorem and a clear route to generality.

**Recommended path:** A → C → B.  
Get a fully verified concrete theorem in the finite one-query or distinguished-query setting first, then abstract.

## Cross-Domain Connections You Must Exploit

This project is strongest if it is not presented as “just cryptography.”

### 1. Probability theory + algebraic extraction
The forking lemma is a **probabilistic coupling theorem** wrapped around a linear algebra identity over a finite field. Make that explicit. The extraction formula is a solved linear system in `ZMod q`; the rewinding lemma is a statement about correlated samples.

### 2. Finite field geometry + proof systems
Two accepting transcripts define two affine lines in transcript space whose intersection reveals the witness. There is a geometric interpretation:
- transcript validity is an affine constraint,
- forking produces two distinct challenge slices,
- extraction is interpolation.

This suggests future formal work on **proof systems as finite-geometry objects**.

### 3. Information theory + security loss
The quantity `ε²/q` is not merely a bound; it reflects entropy loss under rewinding and challenge collision structure. Frame the theorem as a first step toward **formal information-theoretic accounting of reduction loss**.

### 4. Programming languages / semantics
A rewinding adversary is a stateful probabilistic program with controlled replay. Your new `ForkableAdversary` structure can become a semantic object for verified cryptographic game transformations.

### 5. Computational complexity
Concrete reduction loss determines real-world parameter sizes. This is where formal proof meets systems security: a bad constant means larger groups, slower protocols, and weaker deployability.
