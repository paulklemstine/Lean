## Precise theorem targets

You should aim for at least the following three major theorems, with full nontrivial proofs.

### Theorem 1: Substitution-context compatibility of rewriting
This is the infrastructure theorem from which everything else flows.

**Mathematical statement.**  
Let `R` be a rewrite relation on terms. If `s →[R] t`, then for every substitution `σ` and every one-hole context `C`, we have
`C[σ(s)] →[R] C[σ(t)]`.
Equivalently: one-step rewriting is closed under substitutions and contexts.

This is the key mechanism behind equational preservation for orient/simplify/compose/collapse.

**Lean 4 target signature (representative):**
```lean
theorem rewrites_closed_under_subst_and_context
  {Sig Var : Type}
  [DecidableEq Var]
  (R : List (Term Sig Var × Term Sig Var))
  {s t : Term Sig Var} :
  Rewrites R s t →
  ∀ (σ : Subst Sig Var) (C : Context Sig Var),
    Rewrites R (C.fill (Term.subst σ s)) (C.fill (Term.subst σ t))
```

If your concrete rewriting relation is parameterized differently, adapt the statement, but keep the exact mathematical content.

A useful intermediate pair of lemmas:
```lean
theorem rewrites_closed_under_subst ...
theorem rewrites_closed_under_context ...
```

### Theorem 2: Soundness of each concrete completion rule
For each concrete operation, prove that the transformed system has the same equational closure, or at minimum satisfies the abstract soundness obligation required by the framework.

**Mathematical statement.**  
For each concrete rule constructor `ρ`, if `ρ S = S'`, then the equational theories generated by `S` and `S'` coincide:
`EqTh(S) = EqTh(S')`,
or the corresponding abstract step predicate `KBStep S S'` holds.

This should be proved separately for the six rules, not bundled into one opaque theorem.

Representative Lean signatures:
```lean

  ConcreteOrient ord E R s t = some (E', R') →
  KBStep (AbstractState.mk E R) (AbstractState.mk E' R')

theorem concrete_deduce_sound ...
theorem concrete_simplify_sound ...
theorem concrete_delete_sound ...
theorem concrete_compose_sound ...
theorem concrete_collapse_sound ...
```

If the abstract library uses a different state type, match it exactly. The decisive point is that each concrete operation is independently certified.

### Theorem 3: Global simulation theorem from concrete completion to abstract completion
This is the field-opening result.

**Mathematical statement.**  
Every concrete completion derivation induces an abstract completion derivation with the same semantic invariant. Therefore, if the abstract framework proves that fair derivations leading to a terminating/confluent rewrite system are complete, the concrete procedure inherits correctness.

Representative Lean signature:
```lean
theorem concrete_derivation_simulates_abstract
  (steps : List (ConcreteStep Sig Var))
  {S₀ Sₙ : ConcreteState Sig Var} :
  ConcreteDerives steps S₀ Sₙ →
  AbstractDerives (fun A B => KBStep A B) (S₀.toAbstract) (Sₙ.toAbstract)
```

A stronger semantic corollary is highly desirable:
```lean
theorem concrete_completion_preserves_equational_theory
  {S T : ConcreteState Sig Var} :
  ConcreteReachable S T →
  EquationalTheory S = EquationalTheory T
```

### Optional theorem 4: Correctness of certified matching
This is where the executable mathematics becomes algorithmic rather than merely relational.

**Mathematical statement.**  
If `match? p t = some σ`, then `p[σ] = t`.  
If `match? p t = none`, then no substitution instantiates `p` to `t`.

Representative Lean signatures:
```lean
theorem match_sound
  (p t : Term Sig Var) {σ : Subst Sig Var} :
  match? p t = some σ →
  Term.subst σ p = t

theorem match_complete
  (p t : Term Sig Var) :
  match? p t = none →
  ¬ ∃ σ, Term.subst σ p = t
```

This would elevate the project from rewriting infrastructure to a genuine certified symbolic algebra kernel.

## Proof architecture: three viable strategies

### Strategy A: Context-first semantic closure
**Most promising.**

1. Define substitutions and one-hole contexts.
2. Prove separately:
   - substitution compatibility,
   - context compatibility,
   - equational closure under these operations.
3. Use these lemmas as a universal engine to discharge soundness of orient/simplify/compose/collapse.
4. Handle deduce by showing that critical-pair generation produces equations already in the equational theory induced by overlaps.
5. Then prove the concrete-to-abstract simulation theorem by case analysis on concrete steps.

**Why this is best:**  
It isolates the deepest mathematics in reusable closure lemmas. Once these are in place, each completion rule proof becomes conceptual rather than ad hoc. This also aligns best with both rewriting theory and Lean proof engineering.

### Strategy B: Position-indexed rewriting
1. Define term positions explicitly as lists of child indices.
2. Define `replaceAt : Term → Position → Term → Option Term`.
3. Define rewriting as existence of a position where a left-hand side matches.
4. Prove substitution and context closure through position concatenation.
5. Build completion rule soundness on top of these explicit positional witnesses.

**Why this may help:**  
This is closer to textbook rewriting theory and can make critical pair proofs very explicit. It is especially strong if you later want executable critical-pair computation.

**Risk:**  
Position arithmetic in Lean can become bureaucratic unless your term representation already supports indexed argument lists elegantly.

### Strategy C: Inductive closure via generated congruence
1. Define equational theory as the smallest congruence containing the rules.
2. Prove every concrete rule preserves this congruence directly by induction on derivations.
3. Derive rewriting/context/substitution closure as corollaries.

**Why this is elegant:**  
Semantically clean and category-theoretic in spirit.

**Risk:**  
Harder to extract executable content and may obscure the operational structure needed for certified matching and demos.

**Recommendation:** pursue **Strategy A**, borrowing local ideas from B for critical-pair and overlap management.

## Cross-domain connections you must explicitly develop

This project is not just term rewriting. It sits at a surprising nexus.

### 1. Term rewriting ↔ type theory
Substitution is the common infrastructure of:
- first-order term algebra,
- lambda-calculus environments,
- dependent type theory instantiation.

A theorem showing that your substitution action is functorial or compositional,
```lean
theorem subst_comp
  (σ τ : Subst Sig Var) (t : Term Sig Var) :
  Term.subst τ (Term.subst σ t) = Term.subst (τ.comp σ) t
```
connects rewriting semantics directly to the algebra of substitutions familiar from proof theory and logical frameworks.

### 2. Term rewriting ↔ formal language theory
Matching is tree parsing with variables. A soundness/completeness theorem for matching says that pattern matching is a **recognition procedure for a tree language generated by a pattern schema**. This is a concrete bridge to automata on trees and symbolic parsing.

You should state at least one theorem or discussion point in this direction, e.g. the set
`{ t | ∃ σ, subst σ p = t }`
is exactly the language recognized by your matcher.

### 3. Term rewriting ↔ universal algebra / algebraic specification
Completion transforms presentations of algebraic theories into computationally usable rewrite systems. Your free-group test case is not an example tacked on at the end; it is the universal-algebraic proof-of-concept that a presentation can become an executable normalizer.

### 4. Optional stronger bridge: rewriting ↔ category theory
If feasible, observe that substitutions form a category (or at least a monoid action), contexts act functorially, and rewriting is stable under these actions. Even one formal lemma in this direction would make the development conceptually richer.
