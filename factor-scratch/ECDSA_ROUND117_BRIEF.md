# ECDSA brainstorm, round 117 — what is actually left

Third pass. `ECDSA_BRIEF.md` (A–L) and `ECDSA_ROUND116_BRIEF.md` (M–T) came first;
round 115 completed A/D/F/I-baseline and round 116 killed M/N. This file is for what
is *still open after that*, and it starts with the screening result, because the
screening is what makes the remaining list short.

## Why the list is short — the two closure results

1. **Deployment screening (round 15, brief §1).** ECDSA as deployed is over a prime
   field with an essentially prime-order base point (P-256 `n`, secp256k1 `n` and
   Ed25519 `L` verified prime in round 15). Every attack that needs a subfield, an
   extension field, a small trace, a smooth order, or a pairing is therefore vacuous
   *for the deployed scheme*, however good the mathematics is.
2. **Threshold measurement (rounds 115/116).** The plain HNP lattice attack needs total
   nonce leakage `t·ℓ ≈ (1.03, 1.125, 1.25)·log₂ n` at `t = (2, 4, 8)`, and this is
   **independent of the key entropy** — the `b = nbits` slice is the whole surface.
   Beating the floor is impossible; beating the 1.03–1.25× overhead is the only game,
   and it is a lattice-reduction problem, not a new ECDSA problem.

Those two together close: Pohlig–Hellman, MOV/pairings, Weil descent, GHS, XEDNI,
small-trace p-adic, torus NFS, class-field/Kolyvagin reductions, and the
counting-bound version of "small keys make nonce leakage cheaper". Everything else
that survives has either already been measured, or reduced to a Lean theorem, or
appears in the closed table at the bottom of this file.

## What is genuinely still open

### T1 — Endomorphism-ring audit of the deployed curves
**Math.** For an ordinary curve `E/F_p`, `End(E) ⊗ ℚ ≅ ℚ(√(t² − 4p))` where
`t = p + 1 − #E(F_p)` is the trace, and `End(E)` is an order in that imaginary
quadratic field. Computing `#E` (Schoof–Elkies–Atkin) gives `t`, hence the CM
discriminant `d = t² − 4p`, hence the order and its class number `h(d)`. The
security questions this answers: does `h(d)` have exploitable smallness (the
Galbraith–Hess–Smart transport argument moves an instance *around* the isogeny
class, and a small class means a small class of candidate weak curves)? Is the curve
`j`-invariant rigid (extra automorphisms, `j = 0, 1728`)? Did whoever picked the
parameters have a DLP path that the public cannot see?
**Why it is new to this brief:** every other axis treats the curve as a black box;
this one audits the curve itself, and it is the only one that addresses the
"manipulated parameters" threat model at all.
**Status: OPEN. Cheap with PARI/Sage `ellcard` at 256 bits.**
**Falsifier / positive control (non-negotiable):** the audit must first *fire* on a
curve it knows is special — e.g. a `j = 0` curve or one generated by the CM method
with `h(d) = 1`, and a supersingular curve (`t ≡ 0 mod p`, `d` a multiple of `4p`,
embeddings ≤ 6). An audit that reports "nothing found" on P-256/secp256k1 *without*
firing on the planted cases has measured nothing — this is the campaign's rule and it
bites exactly here, because the expected answer on the deployed curves is "nothing".
**Experiment:** for each deployed curve, compute `t`, `d = t² − 4p`, `|d|`, `h(d)`
where feasible, the automorphism group, and the size of the isogeny class; compare
against the planted controls.
**Deliverable:** a table + the explicit negative, *with the controls shown firing*.

### T2 — Batch verification: the acceptance set collapses under summation
**Math.** Single-signature verification checks `x(u₁G + u₂Q) ≡ r (mod n)`. The usual
*batch* scheme (used to amortise verification) instead checks a weighted sum
`Σ a_i(u₁ⁱG + u₂ⁱQⁱ) = O` — and a sum of points is `O` far more often than each
summand is `O`. The acceptance set of the batch check is therefore *not* the
intersection of the individual acceptance sets, and an attacker who can contribute
one signature or one public key to a batch can satisfy a linear relation that no
individual signature satisfies.
**Why it is new to this brief:** the brief covers malleability and related-key
forgery for single signatures (Axis Q). Batch verification is a *different* linear
algebra and it is where the protocol, not the signature, breaks.
**Status: OPEN as a formalisation + attack construction. The protocol-level lesson is
old in the multisig literature; the ECDSA-batch-specific construction and its Lean
statement are not in this brief.**
**Falsifier:** show that for every batch scheme with weights derived from a
collision-resistant hash (the Fiat–Shamir-style fix), no such cancellation exists.
**Experiment:** construct a batch of signatures that are *individually invalid* but
whose weighted sum verifies, for a concrete scheme (deterministic weights; then
hash-derived weights).
**Lean target:** the cancellation identity `Σ(u₁ⁱG + u₂ⁱQⁱ) = O` with each summand
non-trivial — a short additive-group lemma whose interest is entirely in what it
forbids a protocol from assuming.

### T3 — Partial *key* knowledge: interval vs lattice, measured
**Math.** Knowing `ℓ` bits of the private key leaves `2^{nbits − ℓ}` candidates, i.e. an
interval-DLP problem costing `2^{(nbits − ℓ)/2}` group operations (Axis K, running).
Round 16 proved the lattice attack *cannot* use key entropy (the target vector's norm
is dominated by the scaled nonce coordinates). So there are exactly two ways to use
partial key knowledge and one of them is useless — but nobody has measured where the
crossover lies.
**Status: OPEN as a 2-line cost table; both halves exist.**
**Falsifier:** if the lattice attack *can* be made to exploit known key bits by a
different scaling (putting the key coordinate in the dominant position), the round-16
refutation is overturned — that would be the interesting outcome.
**Experiment:** `b` known key bits → kangaroo cost `2^{(n−ℓ)/2}` measured ops vs.
lattice cost `≈ 1.1·nbits` leakage. Table for `ℓ ∈ {8, 16, 32, 64}`.
**Lean target:** none.

### T4 — Is universal forgery reducible to ECDLP?
**Math.** ECDSA's security is established in the generic-group model (Brown), and the
obvious fact is that a forgery requires solving `x(u₁G + u₂Q) ≡ r` — a fixed-point
search over `r` that costs `~√n`, i.e. exactly an ECDLP. But the *reduction* "any
polynomial-time forger for arbitrary `Q` yields a polynomial-time ECDLP solver" is
**not** a theorem, and it is not clear it is true. This is a clean structural
question: is ECDSA "as hard as" ECDLP in the strong sense, or only in the generic
model?
**Status: OPEN, and this is a question about the scheme's *structure*, not about a
parameter choice — the only remaining kind of question the screening results leave
open.**
**Falsifier:** exhibit a forger that works for arbitrary `Q` and provably does not
solve ECDLP (or a provable impossibility of the reduction).
**Experiment:** attempt the standard reductions on a small curve: use a
forging oracle either as a DLP oracle (via `Q`), or via the "choose `z`, observe
`(r,s)`" self-reducibility to build a DLP solver. If the reduction works, it is a
formalizable chain; if it fails, the failure mode is itself the result.
**Lean target:** the *other* direction (`dlog oracle ⇒ forgery`) is trivial and worth
one lemma; the hard direction is the open part.

## Screened closed in this pass — do not open these

| Looked promising | Closed by |
|---|---|
| ECDH oracle + ECDSA signing oracle on the same key | forging needs `Q = dG`, and `d·R` for arbitrary `R` does not give it: the forgery search is a fixed-point search costing `~√n`, i.e. an ECDLP |
| Known key bits fed into the *lattice* | round 16: the target norm is dominated by the nonce coordinates; the Gaussian-heuristic condition has no `b` term |
| Integer-relation / multivariate-Coppersmith form of the signature equation | `X·Y = n² ≫ N = n`, so Coppersmith's bivariate small-root theorems do not apply to one equation; with `t` equations it *is* the HNP, already measured |
| kleptographic structure in nonce streams (linear/`Dual_EC`-style tests) | requires actual nonce streams, which are not observable; the synthetic version tests a PRF for structure it does not have |
| parity/sign bit of `y(Q)` as key information | `sign(y(dG))` is an unpredictable function of `d`; it filters candidates, it does not shrink the space |
| class-field / Kolyvagin / Brauer-group reductions | Galbraith–Gaudry (fetched): *"none of them has been demonstrated to have any practical impact"* |

| axis | verdict | deliverable |

**T3 is closed by composition, and it is now a deployment statement rather than a
table.** Axis K measured `ops = 6.74 * 2^{b/2}` at `63 364` ops/s, giving
`b ≈ 76` within one core-year, `≈ 103` with 10^4 cores, `≈ 116` with 10^6 cores; BSGS
is memory-infeasible above `b ~ 88`. Round 16 showed the lattice threshold is
`t*l* = 288` bits of *nonce* leakage regardless of key entropy. So the two threats for
a `b`-bit key are substitutes, and the honest advice is: low-entropy keys are a
kangaroo problem, and knowing key entropy does not make a lattice attack cheaper. The
lead's verification note corrects the worker's wall-clock column (100x to 1e10x too
large for `b >= 160`, contradicting the same document's own baseline line) — the op
counts, slope, rate and feasibility figures all survive.

**T1 findings.** All five controls fire (supersingular `t=0`; `j=0`; `j=1728`;
anomalous `|t|=1`; CM `D=−163` with `qfbclassno(−163)=1`). On the deployed curves:
P-256, Curve25519, BrainpoolP256r1 and P-384 are clean (generic `Aut={±1}`, isogeny
class `~2^127–2^193`), but **secp256k1 has `j = 0`** — CM by `ℤ[(1+√−3)/2]`
(class number 1), `Aut` of order 6, and `ω ∈ F_p` with `φ:(x,y)↦(ωx,y)` an
automorphism satisfying `φ²+φ+1=0`, i.e. the GLV setting. Verified from first
principles (not via Sage's `j_invariant()`). **No security consequence**: the
attack-relevant quantities are `t = 0` (MOV), `|t| = 1` (Smart/SAS) and a small
isogeny class (transport); secp256k1 has `t` of 129 bits and an isogeny class of
`~2^129` members. The specialness buys an honest user a faster scalar multiplication
and nothing else that is known.
Two audit-design errors were caught and fixed, and both are worth remembering:
`|t²−4p|` measures the *split*, not the CM type (every CM curve has
`|t²−4p| = |D|f² ~ 4p`), and a Montgomery curve must be built as
`[a1,a2,a3,a4,a6] = [0,A,0,1,0]`, not with `A` in the short-Weierstrass `a4` slot.

**T4 findings.** For a verification point `R = (z/s)G + (r/s)Q`, two same-message
signatures satisfy `s₁R₁ − s₂R₂ = (r₁−r₂)Q` (20/20 on both curves), and because
`p < 2n` the `x`-ambiguity is one bit, so the true `(R₁,R₂)` is uniquely identified
from the 4-way candidate set (20/20). The folklore "only `x(R) mod n` is revealed, so
`R` is unrecoverable" is false. Consequence: for same-nonce reuse **across two
different keys**, `R = r(s₁−s₂)⁻¹(Q₁−Q₂)` recovers the verification point from
published data alone (20/20) — but the nonce scalar is still a DLP and the reduction
to `d` does not exist, because the recovered relation is a restatement of the
signature equations.

Both negatives came with a control lesson worth keeping: the T4 match count read
`0` at first purely because the candidate enumeration kept only one of `±y`.
A null from a harness that cannot represent the answer is not a null result.

# ROUND 117 — THIRD OUTCOME: the embedding avenue is closed

`r117/embedding-sweep/RESULT.md`. My own brief called "beating the 1.03–1.25× overhead
the only game in town", and the obvious mechanism is the two free parameters of the
Kannan embedding, `S_i = 2^sigma` and `B = 2^beta`, which rounds 15/16 fixed at
`(sigma = l, beta = nbits)` without testing. Swept a 20-point grid:

- **`sigma = 0` and `sigma = 32` never work, at any `beta`, at any `l` — including
  `l = 256` where the nonce is fully known and the answer is directly computable.** The
  column scaling of the unknown nonce parts is structurally required, not an
  optimisation knob.
- `sigma` and `beta` must be raised together (the embedding is effectively one-parameter):
  `sigma=128, beta=192` fails while `beta=320` works.
- The best cells (`sigma=128/beta=320`, `sigma=160/beta=352`) only **tie** the classical
  `(sigma=l, beta=nbits)`; `sigma=256/beta=384` is strictly worse (`l*=80` vs `72`).
- **Key entropy `b` does not lower the threshold under any of four embeddings**:
  `l* = 72` for every `b in {64,96,128,192,256}` at `sigma` and `beta` where the
  classical value already holds, never approaching the `b/t` the counting bound permits.

So the counting bound is *not* the binding constraint — the norm/gap condition is — and
the 12.5% overhead is a lattice-*reduction*-quality limit, not a modelling choice.
Improving the threshold needs a better reduction (high-block BKZ, sieving), which is what
the round-15 baseline already recorded as the remaining direction. **Do not reopen the
embedding family.**

# ROUND 117 — FOURTH OUTCOME: the overhead is structural, and now it is explained

`r117/bkz-reduction/RESULT.md`. The embedding sweep's closing claim ("the residual 12.5%
overhead is a lattice-reduction-quality limit") was itself a hypothesis. Measured:

- **Reduction strength does not matter.** `l*` is identical for LLL and BKZ blocks
  8/10/14/20/30/40 at both `nbits=128` and `nbits=256`. Since the embedding dimension is
  `t+2 = 6`, a BKZ block >= 6 is **exact SVP** — so exact SVP also fails below the
  threshold. This is not "BKZ was too weak".
- **The obstruction is a shorter INVALID solution.** The embedded target is
  `(d, K_i 2^l, ..., B)` with `B = 2^nbits`, so `|v*|^2 = B^2 + EXCESS` and every candidate
  solution is within a factor `sqrt(2)` of `B`; the competition is decided by the
  `EXCESS`. Exact SVP's shortest `+-B` vector is shorter than the true one by **exactly
  `2*(nbits/t - l)` bits** (16, 8, 0 for `nbits/t = 64`) and it is **invalid** — it lies
  outside the box `d < n, K_i < 2^m`. At the counting bound they merely tie, and a tie is
  not enough because LLL returns one of the tied vectors.
- So `t*l* = (1.03..1.25)*nbits` = the counting bound `t*l > nbits` **plus a tie-breaking
  margin**, and that margin is a property of the instance, not of the algorithm.

**This is the mechanistic answer to "why can't the baseline be beaten", and it was closed
by refuting my own round-117 conclusion rather than assuming it.**

**The one direction it leaves open is now precise:** the obstruction is an out-of-box
competitor, so the way past it is a *tighter box*, i.e. a leakage pattern that constrains
`K` to a set excluding those competitors — concretely middle-of-the-nonce (extended/interval
HNP) leakage, which constrains `K` to an annulus rather than a ball. That is a statement
about leakage pattern, not lattice technique, and it is where the structured-nonce axis
should be aimed.

# ROUND 117 — FIFTH OUTCOME: the recurrence generalisation is OPEN, and the naive
# prediction is wrong

`r117/recurrence-law/RESULT.md`. The one verified positive (LCG with known multiplier,
4–6 signatures, zero leakage) invites generalising to any known homogeneous linear
recurrence of order j, with the tempting prediction `t* = j+1` from counting equations.
**That prediction is false.** The kernel of the stacked system has rank `t+1` (the slack
variables are unknowns too, and they are large), and the box/covolume count is
`M^t(n+M)^t / n^{t-1} >> 1` for every `(M, n, t)`. Implementation verified by finding and
fixing three of my own construction bugs first; the 0/8 grid survives all three.

The verified LCG construction's own comment gives a different bound — `t(ell+m) >= 3m` —
which is not the equation count and which I have not re-derived. So the open question is
precise: **the correct counting bound for a general order-j recurrence**, and then whether
the attack achieves it. Nothing earlier in the campaign is affected; the I2 positive stands
on the worker's construction and was re-run.

Recommended next step (already recorded there): vary the recurrence *inside* the verified
LCG construction rather than re-deriving the construction from scratch.
